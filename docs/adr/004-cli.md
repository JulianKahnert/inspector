# CLI

This ADR defines which functions the `inspector` CLI has. The CLI sends one request per command to the app and prints the answer; the request and response types live once in `InspectorKit` and are shared with the app.

## Commands

The CLI holds no code for any single action. Every command below works for every app, and what an app can do comes from its catalog.

| Command | What it does |
|---|---|
| `inspector apps` | Lists every app found through Bonjour, each checked with `hello`, as one JSON array. An app that does not answer is listed as not live. It is the only command that is not a wire operation. |
| `inspector hello` | Names the app, the full instance name it was reached under, its process ID and the provider answering. |
| `inspector catalog` | Lists every registered action with the payload schema it accepts. |
| `inspector state [path]` | Prints the whole state, or the subtree at a dotted path. |
| `inspector send <path> [json]` | Sends one action and prints its result: whether the effects settled, the new state and the diff. A payload that does not parse as JSON is sent as a string. |
| `inspector send <path> [json] --until <match> [--timeout s]` | The same, but answers only once the state contains the match document ([Conditions](#conditions)). |
| `inspector wait <match> [--timeout s]` | Prints the state as soon as it contains the match document. |

## Options for every command

| Option | What it does |
|---|---|
| `--app NAME` | Picks the app by its full instance name `<app> @ <device>` or by its `<app>` part. Without it, a command works only while exactly one app serves. A full instance name skips the 500 ms wait for a second match ([ADR 001](001-connection.md#naming-and-finding-an-app)); `hello` and `apps` print it. |

## Conditions

`wait` and `send --until` take a condition: a **match document**, one JSON object the state has to contain.

| In the match | Holds when the state has |
|---|---|
| an object | every one of its keys, each value matching in turn; keys are taken as written, so `"settings.detail"` is one key, never a path |
| an empty object `{}` | the key, whatever its value: `{"settings.detail":{}}` asks only that the screen registered |
| an array | an array that starts with matching elements, so `[]` matches any array |
| a scalar | the same scalar; numbers compare by value, so `1` matches `1.0` |

There are no operators. A condition beyond containment, such as `>` or a regular expression, stays a `jq` filter over `inspector state` in a loop of the caller's own.

The app checks the condition itself, never the CLI: right away (for `send`, right after the action settled), again whenever a state reader or an action is registered or cancelled, and every 25 ms in between, until it holds or `--timeout` passes, 3 seconds by default. No check costs a network round trip, and a screen that registers after the action is seen without waiting for the next tick.

- `send --until` answers like `send`: `settled`, the state once the condition held, and the diff against the state before the action.
- `wait` prints the state once the condition held, the same document `inspector state` prints.
- A condition that does not hold in time fails with `EXPECTATION_FAILED`; `detail` carries the last state checked as one line of JSON, so `jq -r .detail | jq` reads it.
- `--timeout` without `--until`, and a match that is not a JSON object, are usage errors.
- An app built with an InspectorKit from before conditions drops `until` and answers right after the action. The CLI checks the answer's state against the match itself and fails with `EXPECTATION_FAILED` rather than report a condition it never saw hold; a `wait` to such an app ends in `BAD_REQUEST`.
- On the wire, `wait` is its own request and answers with the same `sendResult` as `send`. It takes an optional `baseline` to diff against, so a command that changes the app by other means than an action can read the state first, act, and then ask the app to wait, getting the same `settled`, `state`, `diff` answer.

## Output is filtered with `jq`

Every answer is shaped to be queried and filtered with `jq`, because that is how an agent or a shell script picks one value out of it:

```console
$ inspector state | jq '.counter'
$ inspector catalog | jq -r '.actions[].path'
$ inspector apps | jq -r '.[] | select(.live) | .name'
```

- Every answer goes to stdout as exactly one JSON document, never mixed with prose or progress output.
- Keys are sorted, so two answers with the same content are byte-identical and diff cleanly.
- A failure goes to stderr as one JSON error line with exit code 1, so it never ends up in the `jq` input by accident. An agent branches on `code`, never on the message.
- A usage error exits with 64.
- Discovery fails with `APP_NOT_FOUND` after about 5 s without an app, or when `--app` matches none. It fails with `AMBIGUOUS_APP` when several apps match, and the error's `detail` lists their instance names. An app that is found but stops answering ends in `TIMEOUT` ([ADR 001](001-connection.md)). A condition's timeout is added to that bound, so the CLI never gives up before the app does.
