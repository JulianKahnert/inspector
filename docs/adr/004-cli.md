# CLI

This ADR defines which functions the `inspector` CLI has. The CLI sends one request per command to the app and prints the answer; the request and response types live once in `InspectorKit` and are shared with the app.

## Commands

The CLI holds no code for any single action. Every command below works for every app, and what an app can do comes from its catalog.

| Command | What it does |
|---|---|
| `inspector apps` | Lists every app found through Bonjour, each checked with `hello`, as one JSON array. An app that does not answer is listed as not live. It is the only command toward the app that is not a wire operation. |
| `inspector hello` | Names the app, the full instance name it was reached under, its process ID and the provider answering. |
| `inspector catalog` | Lists every registered action with the payload schema it accepts. |
| `inspector state [path]` | Prints the whole state, or the subtree at a dotted path. |
| `inspector send <path> [json]` | Sends one action and prints its result: whether the effects settled, the new state and the diff. A payload that does not parse as JSON is sent as a string. `${NAME}` in the payload is filled from `.inspector/.env` ([Values from `.env`](#values-from-env)). |
| `inspector send <path> [json] --until <match> [--timeout s]` | The same, but answers only once the state contains the match document ([Conditions](#conditions)). |
| `inspector wait <match> [--timeout s]` | Prints the state as soon as it contains the match document. |
| `inspector init [--warm] [--reset] [--workspace path]` | Builds, installs and starts the app through Xcode in a new device interaction session, reads `hello` and `state`, and writes `.inspector/config.json`; with `--warm` it only reads the app that already serves. Prints `config` (the file as written), `hello` and `state` ([Init](#init)). |
| `inspector capture` | Captures the simulator's screen in the session `.inspector/config.json` names and prints `screenshot` and `hierarchy`, the paths of the files Xcode wrote, and `targets`, the controls on the screen ([Targets](#targets)). Writes both paths to `run.json` as `lastScreenshot` and `lastHierarchy`. Talks to Xcode, not to the app ([Commands through Xcode](#commands-through-xcode)). |
| `inspector tap <x> <y>` | Taps the simulator's screen at a point, in points. Prints `gesture`, the command Xcode ran ([Gestures](#gestures)). |
| `inspector tap --target <name>` | Captures the screen, resolves the one target whose identifier or label is the name ([Targets](#targets)) and taps its `hitPoint`. Prints `gesture` and `target`. |
| `inspector swipe <x1> <y1> <x2> <y2> [s]` | Drags from the first point to the second, over the duration in seconds when one is given. Prints `gesture`. |
| `inspector type <text>` | Types the text into the focused field; `${NAME}` is filled from `.inspector/.env` and masked as in `send`. Prints `gesture`. |
| `inspector tap \| swipe \| type … --until <match> [--timeout s]` | The gesture, then the app waits for the match; prints `send`'s answer, diffed against the state before the gesture ([Conditions](#conditions)). |
| `inspector end` | Ends the Xcode device interaction session `.inspector/config.json` names; the app the session started ends with it, an app started otherwise keeps running. Prints `session` and Xcode's own answer under `xcode`, also `Session doesn't exist anymore` for a session that already ended, which Xcode does not flag as an error. Talks to Xcode, not to the app ([Commands through Xcode](#commands-through-xcode)). |

## Options for every command

| Option | What it does |
|---|---|
| `--app NAME` | Picks the app by its full instance name `<app> @ <device>` or by its `<app>` part. Without it, a command talks to the `instance` in `.inspector/config.json`, and without that only works while exactly one app serves. A full instance name skips the 500 ms wait for a second match ([ADR 001](001-connection.md#naming-and-finding-an-app)); `hello` and `apps` print it. |

## The `.inspector/` folder

Separate calls share no process, so what binds them to one app and device lives in a folder in the app's repository root.

**Finding it.** Every command but `apps` looks for `.inspector/` from the working directory upwards and stops at the repository root, the first directory with a `.git` entry, so a repository nested in another one, such as a worktree inside a checkout, never picks up the outer one's folder. Outside a repository the search goes up to `/`. `INSPECTOR_DIR=<path>` names the folder for one call instead, absolute or relative to the working directory.

**Which commands need it.** The folder is optional for the wire commands, so they keep working for a Mac app, a physical device and a debug build nobody set up a folder for:

| Command | Without a folder | With a folder |
|---|---|---|
| `apps` | Works; it is discovery and never looks | Ignores it |
| `hello`, `catalog`, `state`, `wait` | Work as before | `instance` from `config.json` is the default for `--app`; the call is recorded in `run.json` |
| `send` | Works as before, unless the payload has a `${NAME}`: then `NO_CONFIG` | As above, plus `${NAME}` from `.env` |
| `capture`, `tap`, `swipe`, `type`, `end` | `NO_CONFIG` | Work in the session `config.json` names |

`NO_CONFIG` ends a call that cannot work without the folder: a `${NAME}` placeholder with no folder to take its value from, and any command but `apps` and `init` (which creates it) when `INSPECTOR_DIR` names a folder that does not exist, since an explicit path that misses is a mistake to report rather than to guess around. Its `detail` is the path where the folder was expected: `INSPECTOR_DIR`, or `.inspector/` in the repository root, or in the working directory outside a repository. Commands that reach the device through Xcode need the folder's session and simulator and will end in `NO_CONFIG` without it.

**The files.**

| File | Written by | Fields |
|---|---|---|
| `config.json` | only `init`, and a session restart that rewrites `session` | `app` (the `--app` selector), `instance` (the full instance name, the default for `--app`), `bundleId`, `udid`, `session`, `workspace` (the Xcode workspace identifier), `scheme`, `logSubsystem`, `writtenAt`. Every field is optional, so a hand-written file with just `instance` works. |
| `run.json` | every command but `apps`, after it ran, failed or not | `lastStep`: `command`, `arguments` (the whole argument list) and `at`, the call's start in ISO 8601 UTC with milliseconds, so a log read from `at` on covers a failed step. Later commands add their own fields: `capture` and every gesture write `lastHierarchy` and `lastScreenshot`, the files Xcode wrote after the call, and drop a path Xcode did not name rather than keep an older one; each command replaces only its own fields and keeps the rest. |
| `.env` | the developer, or the script that sets up the integration | `NAME=value` per line; blank lines, `#` comments, an `export ` prefix and quotes around a value are allowed, nothing inside a value is expanded |

Both JSON files are written atomically, pretty-printed with sorted keys. A failure to write `run.json` does not fail the call, whose effect already happened.

**Git.** The folder is never committed. A repository that keeps the integration permanently lists `.inspector/` in its `.gitignore`; one that adds the integration only for a debugging session lists it in `.git/info/exclude`, which leaves no trace in the repository's history. When `init` writes the folder into a repository root that ignores it nowhere (`git check-ignore`), it adds `/.inspector/` to `.git/info/exclude` itself, in a worktree to the main repository's; a folder elsewhere through `INSPECTOR_DIR` gets no entry.

### Values from `.env`

`send` replaces `${NAME}` (a letter or underscore, then letters, digits and underscores) in its payload with the value in `.inspector/.env`, and `type` in its text, which Xcode then types; the shell environment is never read. In a payload that is JSON already, the value goes into its strings and keys as text, so a quote in a value cannot break the JSON. Otherwise it goes into the raw argument before that is parsed, so `send counter.set '${VALUE}'` with `VALUE=42` sends the integer 42. A placeholder without a value ends the call with `ENV_MISSING` before anything is sent; the message names every missing placeholder and `detail` lists their names.

Every value filled in is masked in everything the call prints or writes: the answer on stdout, an error's `message`, `detail` and `didYouMean` on stderr, and the arguments in `run.json`. The masking replaces the value wherever it appears, also where the app's state holds it for an unrelated reason, so a short value hides more than its own use. In strings and keys the value becomes `${NAME}`; a number or boolean equal to it becomes the string `"${NAME}"`. Only filled-in values are masked: no key name such as `password` counts, and a `.env` value the payload did not use prints as it is. The masking lasts one call; a later `state` that fills nothing in prints the value.

## Commands through Xcode

Commands that act on the simulator, `init`, `capture`, the gestures and `end`, call Xcode's device interaction tools. Xcode is the MCP server, the CLI one of its clients.

- **One bridge per call, no daemon.** A call starts `xcrun mcpbridge` as its own child process, sends `initialize`, `notifications/initialized` and its tool calls, then closes stdin; the bridge exits about 0.1 s later. Starting it costs 0.1 to 0.2 s until `initialize` answers, rarely 0.6 s. The session lives in Xcode: it outlives every bridge, a new bridge reaches it by its name, and each call into it pushes its expiry of about two minutes back.
- **Approval.** Xcode serves a client only after a human approved it, and recognizes it by the signature of the bridge's direct parent process: team ID plus identifier. The skill's `inspector.sh` signs the binary after every build with an "Apple Development" identity, `INSPECTOR_SIGNING_IDENTITY` or else the first one in the keychain, and the fixed identifier `de.juliankahnert.inspector`, so a rebuild keeps the approval. `swift build` alone leaves an ad-hoc signature that Xcode refuses; `inspector.sh` signs it again on its next call. Without an identity `inspector.sh` fails with `NO_SIGNING_IDENTITY` as a JSON line.
- **Rebuild.** `inspector.sh` resolves its own location with `cd -P`, so it runs the CLI of the checkout it lives in also through the global symlink `~/.claude/skills/inspector`. It builds when the binary is missing or older than anything in `Sources/`, `Package.swift` or `Package.resolved` (directories included, so a deleted file counts), and dates the binary after the build, because an up-to-date build leaves it untouched. The check costs a few milliseconds; a no-op `swift build` on every call would cost 1 to 2 s. A failed build ends in `BUILD_FAILED` after the compiler's output.
- **Session parameter.** `DeviceInteractionSynthesize` takes the session's name as `interactSessionKey`, the other session tools as `interactionSessionKey`; the CLI hides the difference.
- **Session restart.** When a session call meets `Session not found`, the CLI asks the app `hello` under the `instance` in `config.json`. If it answers, the CLI starts the session `inspector-<repository>-<yyyyMMdd-HHmmss>` (UTC) on the `workspace` and `udid` in `config.json`, writes it to `session`, and runs the call once more. If the app does not answer, the call ends in `NO_SESSION`, after the 5 s discovery bound. A session restarts only for a call that works in it, never for `end`.

| `code` | When | Next step |
|---|---|---|
| `NOT_APPROVED` | Xcode refuses this binary | A human confirms Xcode's dialog that approves `de.juliankahnert.inspector`; calling again changes nothing |
| `NO_SESSION` | `config.json` names no session, or the session ended and its app with it | `inspector init` |
| `XCODE_TOO_OLD` | The selected Xcode has no `mcpbridge` | A human selects Xcode 27.2 or newer |
| `XCODE_ERROR` | A tool failed, or the bridge exited before it answered; `message` quotes Xcode, `detail` is its text alone | Read `message` |
| `TIMEOUT` | The bridge did not answer `initialize` within 10 s (30 s after `init` started Xcode), or a tool within its time | Check that Xcode runs |
| `NO_SIGNING_IDENTITY` | `inspector.sh` found no identity to sign with | A human adds an "Apple Development" identity in Xcode > Settings > Accounts |
| `BUILD_FAILED` | `inspector.sh` could not build the CLI; `detail` is the checkout | Fix the checkout, or report it |
| `NO_HIERARCHY` | A capture came back without a readable, non-empty hierarchy file; `detail` is Xcode's answer | Capture again, else read the screenshot |
| `TARGET_NOT_FOUND` | No target has the identifier or label asked for; `detail` lists every target as JSON | Pick one from `detail`, or tap by coordinates |
| `TARGET_AMBIGUOUS` | Targets at more than one point have it; `detail` lists those targets as JSON | Name the identifier, or tap by coordinates |

### Gestures

**Gestures work only in the simulator.** Xcode 27.2 offers no physical device for device interaction, so a gesture on an iPhone or a Mac app is out of reach; reading state and sending actions reach both. A gesture is one call of `DeviceInteractionSynthesize` in the session, with Xcode's own command syntax:

| Command | Sent to Xcode |
|---|---|
| `tap <x> <y>` | `t <x> <y>` |
| `tap --target <name>` | a capture, then `t <x> <y>` at the target's `hitPoint`, in the same bridge |
| `swipe <x1> <y1> <x2> <y2> [s]` | `t <x1> <y1> f <x2> <y2> [s]` |
| `type <text>` | `sender keyboard kbd <text>`; `kbd` takes the rest of the command, and Xcode reads `\u{0008}` as backspace and `\u{000A}` as Return |

- **Answer.** Without `--until`, `gesture` is the command Xcode ran and `target` the target `--target` resolved; Xcode accepting the command is the success, not the app reacting to it. With `--until`, the answer is `send`'s ([Conditions](#conditions)).
- **Order.** `NO_CONFIG` and `NO_SESSION` come before the bridge starts; a target that does not resolve fails before the state is read or anything is tapped.
- **The screen lags the state.** An action that presents a sheet changes the state at once, while the sheet still slides in, and a gesture during that animation can be lost: a swipe that dismisses a sheet failed every time 0.2 s after the state said open, once in two tries after 0.5 s, and never after 1 s. The CLI does not guess animation lengths; the caller pauses after a navigation, and `--until` turns a lost gesture into `EXPECTATION_FAILED`.
- **Time.** In the simulator with a debug build of the CLI: `tap` 1.0 to 1.3 s, `swipe` 1.3 to 1.5 s, `type` 0.9 to 1.0 s, `tap --target` with `--until` 1.5 to 2.1 s, most of it Xcode synthesizing the event and capturing the screen afterwards.

### Targets

`capture` reduces Xcode's hierarchy, an indented text of every element with its frame, to what an agent acts on, so it reads about 1 KB instead of 5 to 25 KB.

- **What counts.** A control (`Button`, `Cell`, `TextField`, `SecureTextField`, `SearchField`, `TextView`, `Switch`, `Toggle`, `Slider`, `Stepper`, `SegmentedControl`, `Picker`, `PickerWheel`, `DatePicker`, `Link`, `Tab`, `MenuItem`, `Icon` and the Mac's controls) with an identifier, label, value or placeholder; a text input also without any. Containers, static text, images and keyboard keys are left out, since a control carries the label of what is inside it.
- **Fields.** `type`, `identifier`, `label`, `placeholder` and `value` where the hierarchy names them, and `hitPoint` as `[x, y]` in points, in hierarchy order. `type` and `placeholder` are there because a text field often has neither identifier nor label. `value` is the text in a field, so a typed value the app's state does not hold can be read here.
- **Parsing.** The value is not quoted and may contain commas; it ends where the known states (`Selected`, `Disabled`, `Keyboard Focused`, `Focused`) begin. A line that does not parse is left out rather than failing the capture.
- **Resolving one.** A target named by identifier or label resolves to exactly one: every target whose identifier or label equals the name, where matches at the same `hitPoint` count as one, since the hierarchy lists some elements twice. None is `TARGET_NOT_FOUND`, several are `TARGET_AMBIGUOUS`.

### Init

`inspector init` takes a repository from nothing to the app's full state in one call, and is the only command that writes `config.json` in full. It never takes a screenshot or reads the hierarchy, never resets the app's data on its own, and never logs in.

**Cold**, the default, for a first run and after every code change:

1. **Workspace.** `--workspace <path>`, else the one `.xcworkspace` in the repository root or up to three levels below it, else the one `.xcodeproj`; hidden directories, `build`, `DerivedData`, `Pods`, `Carthage` and `node_modules` are skipped. None or several end in `BAD_REQUEST` naming `--workspace`.
2. **Xcode.** When no `Xcode` process runs, `xed -b <workspace>` starts it, and the bridge gets 30 s instead of 10 s to answer `initialize`. An Xcode without `mcpbridge` ends in `XCODE_TOO_OLD`.
3. **Open and approve.** `XcodeOpenWorkspace` returns the workspace identifier and the active scheme, opens a workspace that is not open yet, and is the call that makes Xcode show its approval dialog to a human. Xcode answers it only once the human confirmed, so the call waits up to 90 s. Xcode's refusal ends in `NOT_APPROVED`, whose message asks the human to confirm the dialog and run `init` again. No answer in that time ends in `TIMEOUT`, whose message asks the agent to run `init` again: a starting Xcode took 62.9 s once, and an Xcode that still waits for the human answers the next call with its refusal, so the retry ends in `NOT_APPROVED` at once. An open workspace answers in milliseconds.
4. **Scheme and bundle ID.** The active scheme builds, unless `--app` names (by its `<app>` part) another scheme of the workspace: then `XcodeSwitchScheme` makes that one active. `XcodeListTargets` picks the app target, the only one or the one named like the scheme, and `GetTargetBuildSettings` gives `PRODUCT_BUNDLE_IDENTIFIER` and the executable name, which is the name `serve()` advertises by default and so the `--app` selector when none is given.
5. **Session.** `EndSession` of the session the old `config.json` names (its app ends with it), then `StartWorkspaceSession` with a new name `inspector-<repository>-<yyyyMMdd-HHmmss>`, because Xcode rejects a name that was just in use. It asks for the old config's `udid`, or lets Xcode take the scheme's run destination and boot it, and reads the device from the answer's `deviceUUID`. `config.json` is written now, so `inspector end` reaches the session even if the build fails.
6. **Build and run.** `--reset` first runs `xcrun simctl uninstall <udid> <bundleId>`. `InstallAndRun` builds, installs and starts the app, also without a code change, for up to 20 minutes. A build error ends in `XCODE_ERROR` with Xcode's text.
7. **First observation.** `hello` and `state`, with up to three discovery rounds while the new process starts serving. `config.json` gets `instance`, the full instance name `hello` reports, so every later call connects without the 500 ms wait. An app that never serves ends in `APP_NOT_FOUND` or `TIMEOUT` with the next step: check that its debug build calls `serve()`, or pass `--app`.

**Warm**, `--warm`, chosen by the agent when no code changed since the last run; there is no file stamp. It reads `hello` and `state` of the app under `--app`, the config's `instance` or the only serving app, updates `app` and `instance`, and leaves Xcode and the session alone. It only finds an app that runs outside a session, such as one started with `xcrun simctl launch` of the installed build, because a session's app ends when the session expires. An app that does not serve ends in `APP_NOT_FOUND` or `TIMEOUT` with the next step: `init` without `--warm`.

`logSubsystem` is the bundle ID's vendor prefix, its first two components plus a dot (`de.juliankahnert.` for `de.juliankahnert.RoommateAlbert`), which `logs.sh` reads as a prefix: the app and its packages logging under their own subsystems are covered alike. A bundle ID with fewer than three components is taken whole.

Measured with Xcode 27.2 running, the workspace open and the app's build up to date: cold 10.9 to 11.5 s, of which 0.25 to 0.29 s before `InstallAndRun` and about 4 to 4.5 s from the app's process start to the answer; warm 62 to 100 ms.

## Conditions

`wait` and `send --until` take a condition: a **match document**, one JSON object the state has to contain.

| In the match | Holds when the state has |
|---|---|
| an object | every one of its keys, each value matching in turn; keys are taken as written, so `"settings.detail"` is one key, never a path |
| an empty object `{}` | the key, whatever its value: `{"settings.detail":{}}` asks only that the screen registered |
| an array | an array that starts with matching elements, so `[]` matches any array |
| a scalar | the same scalar; numbers compare by value, so `1` matches `1.0` |

There are no operators. A condition beyond containment, such as `>` or a regular expression, stays a `jq` filter over `inspector state` in a loop of the caller's own.

The app checks the condition itself, never the CLI: right away (for `send`, right after the action settled), again whenever a state reader or an action is registered or cancelled, and every 25 ms in between, until it holds or `--timeout` passes, 3 seconds by default. No check costs a network round trip, and a screen that registers after the action is seen without waiting for the next tick.

- `send --until` answers like `send`: `settled`, the state once the condition held, and the diff against the state before the action.
- `wait` prints the state once the condition held, the same document `inspector state` prints.
- A condition that does not hold in time fails with `EXPECTATION_FAILED`; `detail` carries the last state checked as one line of JSON, so `jq -r .detail | jq` reads it.
- `--timeout` without `--until`, and a match that is not a JSON object, are usage errors.
- An app built with an InspectorKit from before conditions drops `until` and answers right after the action. The CLI checks the answer's state against the match itself and fails with `EXPECTATION_FAILED` rather than report a condition it never saw hold; a `wait` to such an app ends in `BAD_REQUEST`.
- On the wire, `wait` is its own request and answers with the same `sendResult` as `send`. It takes an optional `baseline` to diff against, so a command that changes the app by other means than an action can read the state first, act, and then ask the app to wait, getting the same `settled`, `state`, `diff` answer.
- A gesture with `--until` does exactly that: `state`, the gesture through Xcode, then `wait` with that state as `baseline`. Its answer is `send`'s, `settled` always `true`. The gesture has happened when the condition fails, and against an app from before conditions the `wait` ends in `BAD_REQUEST` after the gesture.

## Output is filtered with `jq`

Every answer is shaped to be queried and filtered with `jq`, because that is how an agent or a shell script picks one value out of it:

```console
$ inspector state | jq '.counter'
$ inspector catalog | jq -r '.actions[].path'
$ inspector apps | jq -r '.[] | select(.live) | .name'
```

- Every answer goes to stdout as exactly one JSON document, never mixed with prose or progress output.
- Keys are sorted, so two answers with the same content are byte-identical and diff cleanly.
- A failure goes to stderr as one JSON error line with exit code 1, so it never ends up in the `jq` input by accident. An agent branches on `code`, never on the message.
- A usage error exits with 64.
- Discovery fails with `APP_NOT_FOUND` after about 5 s without an app, or when `--app` matches none. It fails with `AMBIGUOUS_APP` when several apps match, and the error's `detail` lists their instance names. An app that is found but stops answering ends in `TIMEOUT` ([ADR 001](001-connection.md)). A condition's timeout is added to that bound, so the CLI never gives up before the app does.
- `NO_CONFIG` and `ENV_MISSING` come from the CLI itself, before any request is sent ([The `.inspector/` folder](#the-inspector-folder)).
